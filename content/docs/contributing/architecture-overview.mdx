## Overview

Two repos, one product: `web` (Next.js, App Router) renders the UI and calls
`server` (.NET) over a REST API, plus SignalR hubs for live game state
(submissions, lobby updates). Auth0 issues the tokens both sides trust.

### Server

The backend server is built based on
[Clean Architecture](https://github.com/jasontaylordev/CleanArchitecture)
with [CQRS](https://martinfowler.com/bliki/CQRS.html), and
[domain driven design (DDD)](https://martinfowler.com/bliki/DomainDrivenDesign.html).
The solution is broken up into these projects:

| Project                    | Owns                                                                          |
| -------------------------- | ----------------------------------------------------------------------------- |
| `StackDuel.Domain`         | Entities, value objects, domain logic - no framework dependencies.            |
| `StackDuel.Application`    | Use cases / handlers that orchestrate domain objects.                         |
| `StackDuel.Infrastructure` | EF Core, repositories, external services (Judge0, blob storage, message bus). |
| `StackDuel.Api`            | HTTP endpoints, SignalR hubs, and auth wiring                                 |

<Accordions type="multiple">
<Accordion title="StackDuel.Domain">

The `StackDuel.Domain` project owns the core business logic of the
application. It has no external dependencies and can theoretically be lifted
and shifted to a new solution. Each slice of the business (Domain) is
divided by its bounded context. For example, Games, Submissions, Users,
Problems, Campaigns, and Achievements are all separate business processes.

`SeedWork` holds all the shared DDD primitives: Entity, AggregateRoot,
IDomainEvent, DomainException, plus the interfaces IRepository/IUnitOfWork
(not implementations - those live in Infrastructure). We used a shared
namespace so that all DDD building blocks behave consistently and have
equal event-raising behavior.

Entities enforce invariants themselves. State transitions are methods on
the aggregate, not something the application layer sets directly on it. The
aggregate decides whether a transition is valid and raises domain events
(`IAggregateRoot.PopDomainEvents()`) when something worth reacting to
happened.

Domain entities are the source of truth for how the business actually
operates - they own the logic, not just the data.

In short: `StackDuel.Domain` answers "what are the rules of the business",
what a Game is allowed to do, when a Submission is complete, what makes a
Campaign valid, with no opinion on HTTP, SQL, or messaging.
`StackDuel.Application` orchestrates use cases against it,
`StackDuel.Infrastructure` persists and transports it, but the domain layer
itself stays framework-agnostic and, ideally, the one place you can trust
to be correct just by reading the code.

<Callout type="warn" title="Keep the domain project pure">
  Domain should never reference Application, Infrastructure, Api, or any
  third-party package.
</Callout>

</Accordion>
<Accordion title="StackDuel.Application">

The `StackDuel.Application` project owns how the business logic gets used.
It's essentially what happens, in what order, and who gets told about it.
This project sits between the Api and Domain layers, orchestrating calls
into the domain model rather than deciding the rules itself.

This project is built on top of the **CQRS** design pattern via
**MediatR**. A command handler's job is narrow: load the aggregate through
a repository interface, call the domain method that actually enforces the
rules (e.g. `game.RecordProblemSolved(...)`), persist via `IUnitOfWork`,
and return a result.

**Events** hold the `INotificationHandler` implementations that react to
domain events the aggregates raise - the side effects that aren't "the core
use case." For example push notifications, derived projections like
leaderboard updates, or follow-on commands against other aggregates.

**Services** are the application-level collaborators a handler reaches for
when logic needs to span multiple aggregates/repositories, so handlers
themselves stay thin. This is also how the rest of the backend reaches the
application layer, all the way up to the Api layer.

So where `StackDuel.Domain` is "what's true and what's allowed,"
`StackDuel.Application` is "what happens, in what order, and who gets told
about it" - it drives the domain model to fulfill a request, but isn't
where the actual business invariants are decided.

</Accordion>
<Accordion title="StackDuel.Infrastructure">

This project references both **Application** and **Domain**, and nothing
references it back. Domain and Application define the interfaces
(IRepository, IUnitOfWork, IGameNotificationService, IGameProblemCompleter,
etc.) without knowing how they're fulfilled. Infrastructure is where those
actually get implemented, against Postgres, message buses, blob storage,
whatever third party resource is needed. This isolates all those
dependencies from the business logic so they're easier to swap out later
if we ever need to.

This project also contains the code execution engine, where it defines the
integration with our 3rd party library [Judge0](https://judge0.com/).

</Accordion>
<Accordion title="StackDuel.Api">

Main interface into the backend server. This contains Hubs as well for
SignalR.

</Accordion>
</Accordions>

### Web

The front end is built on top of Next.js to provide better SEO and
performance. We also use Shadcn, Tailwindcss, React Query, and Zustand.
This tech stack helps speed up our development by providing rapid
prototyping, flexible state management, and plenty of out-of-the-box
components.

Each feature area lives under `src/domains/<name>/` and typically contains
its own `components/`, `lib/`, `models/`, `api/` (React Query hooks), and
`forms/` - the domain owns everything specific to it. `src/shared/` is for
code with no single owning domain: layouts, the shadcn-based `ui/`
component library, auth guards, and `router-config.ts`, the single source
of truth for every app route.

Pages under `src/app/` stay thin - they fetch/compose and delegate the
actual UI to a `src/views/<area>/*-layout.tsx` component.
